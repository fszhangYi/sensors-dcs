## 1. 客观评价（对 DeepSeek 方案）

### 说得对的部分

| 点 | 为何采纳 |
|----|----------|
| 原始大文件 ≠ DB 行；对象存储 / 目录树存字节，库里存索引与语义 | 与 DCS `states/` + 视频文件分工一致 |
| 控制域与数据域分层；Flink 不做硬实时 | 防止架构图把 RTOS/CAN 和数仓画成一条热路径 |
| 对齐质量、丢帧、任务结果应变成**可查询字段** | 正是 E1–E4 / M3 / `align_quality` 在做的事 |
| 「融合查询」适合**事后**难例挖掘与质检，不是在线门禁 | 与「质量指标先落盘再筛」一致 |
| Demo 可先 DuckDB / 本地表，不必一上来 Doris 集群 | 避免空转运维 |

### 说得过满 / 不适配现状的部分

| 点 | 问题 |
|----|------|
| **MinIO → Flink → Paimon → Doris** 作为下一跳默认答案 | 单站 / 小站数 Episode 落盘场景，Python asof + sidecar 已够用；上 Flink 是换运行时，不是对齐精度 magically 变好 |
| **「百元/月跑通整套」** | 现金可以很低，**时间与认知成本**才是主账：Flink Watermark/状态、湖表 Compaction、分析引擎运维。对话把运维成本低估了 |
| **工站机器兼职跑 Flink + MinIO + 分析引擎** | 采集机 CPU/磁盘抖动会直接伤录制；生产采集与重计算应隔离 |
| **湖格式三选一写进近期交付** | Iceberg/Paimon/Lance 选型本身不是当前瓶颈；当前瓶颈是 **FT/触觉未进 DCS episode**、金标飞轮、对齐契约写清 |
| **职业 ROI / 35–50K** | 招聘市场叙事，不能当工程排期依据 |
| **Flink = 更正式的时间戳对齐** | 正式的是**事件时间语义**；时钟源、`hw_ts`、腕-指标定 Flink 替代不了（此前已论证） |

### 一句话总评

DeepSeek 画的是一条**合理的中长期数据平台演进图**，不是**本仓库未来 1–2 个季度的必做清单**。  
采纳其**分层与入库原则**；推迟其**分布式流批与湖仓引擎**，直到「能稳定录、能量化、能检索 Episode」在现栈闭环。

## 2. 修订后的目标（按优先级）

**P0 — 把现有数采变成可信资产（本仓主线）**

1. `ft` / `tactile` 进 DCS agent → `states/*.jsonl`（见腕-指构想 P0）。  
2. 时间戳契约文档化：`t_wall` vs `hw_ts`、乱序/迟到容忍、`align_quality` 门控（**语义可借 watermark 思想，实现仍用现有 filter**）。  
3. M1 辅助标注飞轮 + E1 金标对照；质量字段（丢帧、对齐分、outcome、tags）可汇总。

**P1 — 边缘缓冲与搬迁（有离线/多机痛点再上）**

4. 采集机本地目录或**单机 MinIO** 只做「原始 + export 产物」的 S3 视图，便于中转/上云；**不对齐逻辑绑死 MinIO**。  
5. 多机已有 session gather / SMB 路径时，优先补强现有搬迁，而不是平行再造一套对象存储运维。

**P2 — 流式对齐与湖表（规模触发后再上）**

触发条件（满足 ≥2 条再立项）：

- 多站持续写入，后处理窗口无法过夜跑完；或需要**秒～分钟级**规范层刷新。  
- 明确要跨 Episode **SQL + 向量**难例挖掘，且 DuckDB/本地 parquet 已顶不住。  
- 有专人（或可接受的外包）扛 Flink/湖表运维，采集机与计算机分离。

届时再选：Flink（或轻量替代）+ 一种湖格式（有 Flink 中心则偏 Paimon，否则 Iceberg/parquet 亦可）+ 按需 Doris/StarRocks 或继续 DuckDB。

**P3 — 模型闭环（与数据底座解耦排期）**

6. π0.5 / ACT 后训练：建立在 **P0 数据可筛、可导出** 之上；不与 Flink 绑定。  
7. 简历叙事：产线工站 → 数据质量可量化 →（可选）后训练因果；不堆未落地的组件名。

## 3. 目标扇出形态（你提出的三路并行 — 已采纳为远期骨架）

你的意图：

```text
传感器 → 采集端 → 三路并行
                 ├─► MinIO（存档）
                 ├─► Kafka → Flink（处理 / 对齐）
                 └─► WebRTC → 前端（实时展示）
```

### 3.1 评价

| 判断 | 说明 |
|------|------|
| **方向对** | 存档 / 计算 / 预览职责分离，比「一条链路串 MinIO 再进 Flink」清晰 |
| **采集端必须是唯一扇出点** | 三路消费的应是**同一套带时间戳的帧/状态**；禁止传感器驱动被三套客户端各采一遍 |
| **与本仓契合** | 采集端 ≈ 今日 `sensors` + `sensors-dcs` agents；WebRTC 路已有 webrtc-preview / DCS 预览条，应复用而非重开一路抓相机 |
| **Kafka+Flink 仍是规模件** | 单站时可用「落盘 + 后处理 asof」代替 Kafka→Flink；上 Kafka 的理由是**多消费者解耦与背压**，不是对齐本身 |
| **MinIO 存档 ≠ 训练就绪** | MinIO 放原始对象 + episode 树；对齐后的规范事件仍建议另前缀/另桶，或由 Flink sink 写出 |

### 3.2 每路放什么（约束）

| 路 | 宜承载 | 不宜 |
|----|--------|------|
| **MinIO** | 原始视频/点云/episode 目录、export 产物、URI+元数据 | 当实时总线；让前端直接扫桶做预览 |
| **Kafka→Flink** | 轻量状态/事件（关节、ft、触觉摘要、对齐标记）；可选关键帧索引 | 未经抽帧的多路原视频塞满 Kafka；Flink 抢采集机核 |
| **WebRTC→前端** | 相机预览、低延迟人看 | 当金标存档；当对齐真相源 |

硬规则：

1. **录制真相源**仍是采集端落盘（今日 `episode/`）；MinIO 是其对象化镜像或异步上传，故障时不能只靠 Kafka。  
2. **WebRTC 与存档解耦**：预览丢帧不影响 MinIO/Kafka；Kafka 积压不影响预览。  
3. **Flink 不进采集热路径**：消费 Kafka 的进程跑在旁路机或非录制优先级 cgroup。  
4. 先有 **P0 多模态进 episode**，再扇出；空管道上的三路并行没有简历与产线价值。

### 3.3 落地顺序（三路不要同时开工）

```text
阶段 A（现有加强）  采集端 = DCS：落盘 + 现有 viz/WebRTC 预览
阶段 B              落盘目录 → 单机 MinIO（或 mc mirror），验证搬迁
阶段 C              采集端旁路 producer → Kafka（仅状态/事件 topic）
阶段 D              旁路机 Flink 消费 → 对齐/质量 → 写回 MinIO 规范前缀
```

阶段 A/B 不依赖 Kafka；C/D 满足 §2 P2 触发条件再开。

## 4. 架构图

### 近端（阶段 A — 现在）

```text
传感器 → hik-sensors → sensors-dcs（采集端）
                           │
                           ├─► episode/ 落盘（真相源）
                           ├─► 后处理 asof / align_quality / M1…
                           └─► WebRTC / viz（已有预览能力，人看）
```

### 目标扇出（阶段 B–D）

```text
传感器 → 采集端（唯一扇出）
            │
            ├─► MinIO          存档（原始 + 日后规范前缀）
            ├─► Kafka → Flink  处理（准实时对齐 / 质量标记）〔旁路机〕
            └─► WebRTC → 前端  实时展示（复用 webrtc-preview）
```

## 5. 明确不做 / 缓做

| 项 | 决定 |
|----|------|
| 为对齐而上 CAN 总线 | **不做**；时间戳来源按现有接口补齐 |
| 采集热路径嵌入 Flink / 与录制抢核 | **不做** |
| 传感器三开（MinIO、Kafka、WebRTC 各采一次） | **不做** |
| 全分辨率多路视频进 Kafka | **不做**（预览走 WebRTC，存档走 MinIO） |
| Demo 阶段上 3FE+3BE / MinIO 多节点 / Kafka 集群高可用 | **缓做** |
| 同时深挖 Iceberg+Paimon+Lance | **不做**；需要时只选一条写入路径 |
| 用分析引擎或 WebRTC 替代金标与落盘真相 | **不做** |
| 把对话薪资数字写进交付验收 | **不做** |

## 6. 90 天建议排期（工程向）

| 周 | 交付 | 完成定义 |
|----|------|----------|
| 1–3 | FT/触觉 DCS agent + 示例 YAML + 一盘真 episode | `states/` 有 ft/tactile；viz 可见 |
| 3–5 | 对齐契约短文 + `align_quality` 进日常门控 | 坏时钟/高丢帧 episode 可拒收或标 warn |
| 5–8 | M1 预填 + 金标差异表 | 停录能改、能导出对照 |
| 并行 | 腕-指滑移或抓取对比的**小样本实验设计**；巩固现有 WebRTC 预览 | 有基线表；预览不挡录制 |
| 按需 | 阶段 B：episode → 单机 MinIO | 可 `mc mirror` / 断网摆渡 |
| 仅当 P2 触发 | 阶段 C–D：Kafka 事件 topic + 旁路 Flink | 用重放证明；采集机无 Kafka/Flink 抢核 |

## 7. 成本（修订口径）

| 类型 | 近端真实成本 | 说明 |
|------|----------------|------|
| 现金 | 低（盘、可选单机 MinIO/OSS） | 同意「可以很省」 |
| 工程时间 | **主成本** | P0 接线与实验 ≫ 装 Doris / Kafka |
| 采集机资源 | 需保护 | Flink/Kafka broker 放旁路；WebRTC 限路数与码率 |
| 上云 | 按实际 TB 与下行流量另算 | 勿用「100GB × 几元」外推产线全量 |

对话「5–70 元/月」只适合**验证级数据量 + 工站兼职计算**；一旦全量视频上云或分析引擎常驻，账单与运维会上台阶——计划中按触发条件升级，不按最低 demo 价做产能假设。

## 8. 面试 / 对外怎么讲（修订）

**推荐：**  
「采集端统一扇出：落盘存档、（演进）流式处理、WebRTC 预览三路并行；当前工站已跑 sensors→DCS，补力觉与质量门控；Kafka/Flink/MinIO 按负载触发上，不挡产线录制。」

**避免：**  
「已经三路全开 MinIO+Kafka+Flink+WebRTC」——若阶段 C–D 未满足触发条件，属于透支。
